# Veloo 제품 디자인 스펙

Veloo 화면 구조와 시각 의사결정을 고정하는 기준 문서. 세부 토큰은
[디자인 시스템](design-system.md), 모바일 내비게이션은
[캡슐 독 스펙](capsule-dock-spec.md) 참조.

## 1. 제품 정의

연구자의 계획, 탐색, 번역, 모델 분석, 개념 학습을 연결하는 개인 연구 작업 공간.

### 디자인 목표

- 연구 콘텐츠가 장식보다 먼저 인식되는 편집 도구
- 낮은 시각적 소음과 명확한 정보 위계
- 동일 역할에 동일 구조를 적용하는 예측 가능한 인터페이스
- 데스크톱의 작업 효율과 모바일의 탐색 효율을 함께 보장
- 마케팅 화면과 실제 제품 화면 사이의 시각 언어 일치

### 비목표

- 화면마다 다른 카드 문법 도입
- 장식 목적의 글래스 효과 확대
- 기능 구분 목적의 임의 색상 추가
- 페이지마다 새로운 헤더, 검색창, 빈 화면 구조 도입
- 다크 모드 토글 없는 다크 스타일 추가

## 2. 디자인 결정

### D-001 단일 시각 언어

- 기본 배경: `--bg-canvas`
- 작업 패널과 카드: `--bg-base`
- 주요 행동과 선택 상태: `--accent`
- 오류와 삭제: `--c-error`
- 신규 색상값 직접 작성 금지
- 장식보다 정렬, 간격, 타이포그래피를 우선

### D-002 페이지 계열

| 계열 | 화면 | 레일 | 기본 구조 |
| --- | --- | --- | --- |
| 계획 | Tasks, Calendar | 전용 작업 레이아웃 | 소개 > 요약 > 목록 또는 캘린더 |
| 탐색 | Papers, Concepts | `--page-reading-max` | 헤더 > 검색 > 안내 또는 결과 |
| 처리 | Translate, Models | `--page-content-max` | 헤더 > 입력 > 작업 상태 > 결과 |

- 계열 내부의 헤더, 컨트롤, 상태 표현 공유
- 탐색 계열과 처리 계열 사이의 레일 차이만 허용
- 페이지 전용 예외보다 공유 컴포넌트 확장 우선

### D-003 정보 위계

각 화면의 시각적 우선순위:

1. 현재 작업의 제목과 핵심 행동
2. 입력 또는 검색 컨트롤
3. 결과와 진행 상태
4. 설명, 예시, 보조 정보
5. 기록과 부가 기능

- 상시 노출 핵심 행동 1개 원칙
- 기록 기능은 `HistoryDropdown` 사용
- 설명과 예시는 핵심 입력 아래의 보조 정보로 제한
- 비어 있는 결과 공간에 대형 통계 또는 기록 배치 금지

### D-004 공통 페이지 골격

```text
PageHeader
PrimaryControl
PageGuide 또는 PageEmptyIntro
ResultContent
StatePanel
```

- `PageHeader`: 아이콘, 키커, 제목, 설명 담당
- `WorkspaceControls`: 검색, 업로드, 실행 행동 담당
- `PageGuide`: 사용 순서와 짧은 안내 담당
- `PageEmptyIntro`: 검색 또는 입력 전 빈 화면 담당
- `StatePanel`: 로딩, 오류, 결과 없음 담당
- 동일 역할의 마크업과 CSS를 기능 폴더에서 재정의하지 말 것

### D-005 타이포그래피와 간격

- 워드마크 외 텍스트: `--font-sans`
- 페이지 제목: `--fs-section` 이상, 기능별 임의 크기 금지
- 본문: `--fs-body`
- 보조 정보: `--fs-meta`
- 간격: `--space-xs`부터 `--space-2xl`까지 토큰만 사용
- 카드 내부 패딩 기본값: `--space-xl`
- 페이지 섹션 간격 기본값: `--page-section-gap`
- 모바일 입력 글자 크기: 16px 이상
- 본문과 컨트롤의 좌측 정렬 유지

### D-006 컴포넌트 표면

- 카드 모서리: `--radius-lg`
- 입력과 버튼 모서리: `--radius-sm` 또는 `--radius-md`
- 캡슐 모서리: 선택 세그먼트와 짧은 상태 배지에만 허용
- 카드 그림자: `--shadow-card`
- 카드 중첩: 최대 2단계
- 테두리: `--border-subtle`
- `--bg-additive`: 필터 트랙, 진행률 트랙, 작은 웰에만 사용

### D-007 아이콘

- 기본 아이콘: `lucide-react`
- 데스크톱 내비게이션: 15px
- 페이지 헤더와 빈 화면: 공유 컴포넌트가 크기 결정
- 의미가 같은 기능에 같은 아이콘 사용
- SVG (Scalable Vector Graphics) 직접 작성은 브랜드 마크와 라이브러리 미지원 도형에만 허용
- 모바일 하단 독의 Heroicons 예외는 캡슐 독 스펙 유지

### D-008 이미지

- 제품 설명을 보조하는 이미지에만 GPT 생성 이미지 사용
- 마케팅 히어로, 논문 탐색, 모델 학습처럼 역할이 다른 장면에 별도 이미지 사용
- 제품 화면 내부의 입력, 결과, 상태를 이미지로 대체 금지
- 이미지 위에 제품 미리보기 전체를 덮는 레이아웃 금지
- 장식 이미지의 빈 대체 텍스트와 `aria-hidden` 적용
- 공개 마케팅 자산 경로: `frontend/public/marketing/`
- 생성 이미지 방향: 아이보리 배경, 녹색 계열, 절제된 입체 편집 스타일
- 생성 이미지 안의 문자, 로고, 워터마크 금지

### D-009 모션

- 모션 목적: 상태 변화, 공간 이동, 직접 조작 피드백
- 장식 목적의 무한 반복 모션 금지
- 기본 전환 시간: 150ms부터 220ms
- 큰 화면 진입 모션 상한: 900ms
- `prefers-reduced-motion` 대응 필수
- 레이아웃 이동보다 `transform`과 `opacity` 우선
- 모바일 하단 독의 별도 물리감은 캡슐 독 스펙 유지

### D-010 반응형

- 데스크톱: 고정 좌측 내비게이션과 넓은 작업 레일
- 모바일: 하단 내비게이션과 단일 열 콘텐츠
- 모바일에서 보조 사이드바 제거
- 모바일 카드와 입력의 가로 스크롤 금지
- 터치 대상 최소 높이 44px
- hover 전용 핵심 행동 금지
- 스크롤 컨테이너의 `scrollbar-gutter: stable` 적용

## 3. 화면별 계약

### Tasks

- 구조: `PageHeader > TodoSummaryBar > TodoList`
- 전역 내비게이션과 중복되는 페이지 전용 세로 내비게이션 금지
- 작업 상세 선택 전 대형 빈 패널 노출 금지
- 우선순위 표현은 `priority.ts`만 사용

### Calendar

- Tasks와 같은 계획 계열 헤더 사용
- 일정 밀도를 해치지 않는 최소 장식
- 우선순위 색상은 `priorityAccent`만 사용

### Papers와 Concepts

- 동일한 읽기 레일과 검색 구조
- 검색 전 안내는 검색 컨트롤 바로 아래 배치
- 아이콘, 제목, 설명은 `PageEmptyIntro`로 통일
- 추천 검색어는 설명 문단과 분리된 예시 그룹으로 배치

### Translate와 Models

- 동일한 분석 레일과 입력 중심 구조
- Translate의 방향 화살표 유지
- Models의 최근 분석 상시 대형 노출 금지
- 입력 완료 전 결과 패널보다 입력 행동을 강조

### Marketing

- 실제 제품의 내비게이션과 화면 구조를 축약해 표현
- 제품에 없는 가상 인터페이스 표현 금지
- 히어로 이미지와 제품 미리보기의 독립된 시각 영역 보장
- 기능 카드보다 제품 가치와 작업 흐름을 먼저 설명
- 이미지별 역할 중복 금지

## 4. 접근성과 콘텐츠

- 화면 문자열은 `frontend/src/shared/i18n/`에서 관리
- 한국어, 영어, 중국어 키 동시 추가
- 아이콘 단독 버튼의 `aria-label` 필수
- 로딩 상태의 `role="status"`와 상태 문구 제공
- 색상만으로 선택, 오류, 우선순위를 표현하지 말 것
- 장문 제목과 번역문을 고려한 유동 높이 사용
- 키보드 포커스 표시 제거 금지

## 5. 완료 기준

프론트엔드 디자인 변경 완료 조건:

- 기존 공유 컴포넌트 재사용 검토 완료
- 신규 색상값과 화면 문자열 하드코딩 없음
- 같은 계열 화면의 레일과 시작선 일치
- 360px 모바일 폭에서 가로 넘침 없음
- 1280px 데스크톱 폭에서 핵심 행동과 결과의 위계 확인
- 로딩, 오류, 빈 상태, 결과 상태 확인
- 한국어, 영어, 중국어의 레이아웃 유지
- `prefers-reduced-motion` 대응 확인
- `cd frontend && npm run build` 성공
- 관련 문서와 `TODO.md` 갱신

## 6. 변경 절차

1. 기존 결정 번호와 공유 컴포넌트 확인
2. 기존 규칙으로 해결 가능한 변경은 코드만 수정
3. 신규 패턴이 필요한 변경은 결정 문서 수정부터 진행
4. 신규 토큰보다 기존 토큰 조합 우선
5. 대표 화면 1개에서 검증 후 같은 계열에 적용
6. 빌드와 문서 검사 통과 후 커밋

### 예외 기록 형식

```text
E-001
대상: 화면 또는 컴포넌트
기존 결정: D-번호
예외 사유: 기존 규칙 적용 불가 근거
범위: 적용 파일과 화면
종료 조건: 예외 제거 또는 정식 결정 승격 조건
```

- 예외 번호 없는 페이지 전용 규칙 추가 금지
- 반복되는 예외 2건 이상 발생 시 공통 결정 승격 검토
- 디자인 변경 커밋 메시지에 관련 결정 번호 병기 권장
