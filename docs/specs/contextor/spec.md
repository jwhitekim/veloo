# Contextor Specification

## Purpose

영어 단어나 짧은 구를 입력하면 ML/DL 논문에서 쓰이는 맥락별 의미를 구조화된 JSON으로 설명하는 capability. `/contextor` 경로로 마운트.

## Requirements

### Requirement: 단어 조회
The system SHALL accept a text query and return a structured JSON explanation of its ML/DL usage contexts, generated by an AI provider.

#### Scenario: 정상 조회
- GIVEN 인증된 사용자(전역 `AuthMiddleware`가 `request.state.user_id` 설정)
- WHEN `POST /api/lookup`에 `{"text": "trials"}`(LookupRequest) 전송
- THEN AI 프로바이더로부터 받은 응답에서 JSON을 추출해 `{"query", "hasMlUsage", "cases": [...], "note"}` 형태로 반환
- AND `cases`의 각 항목은 `{"label", "term", "meaning", "exampleEn", "exampleKo"}` 필드를 가짐

#### Scenario: 빈 문자열 입력
- WHEN `POST /api/lookup`에 `{"text": ""}` 또는 공백만 있는 문자열 전송
- THEN 400과 `{"error": "단어가 비어 있습니다."}` 반환

#### Scenario: ML 용법이 없는 단어
- GIVEN 입력 단어가 ML/DL 맥락에서 특수 용법이 없음 (예: "banana")
- WHEN `POST /api/lookup` 호출
- THEN `hasMlUsage: false`, `cases: []`, `note`에 특수 용법 없음을 설명하는 문자열을 반환

#### Scenario: cases 개수 제한
- WHEN AI가 응답을 생성
- THEN `cases` 배열은 최대 5개까지만 포함 (System 프롬프트 제약 — 서버 측 강제 검증은 없음)

#### Scenario: AI 호출 또는 JSON 파싱 실패
- GIVEN AI 프로바이더 호출 중 예외가 발생하거나 응답에서 JSON 객체(`{`...`}`)를 찾지 못함
- WHEN `POST /api/lookup` 처리 중 오류 발생
- THEN 502와 `{"error": "조회 중 오류가 발생했습니다. 잠시 후 다시 시도해주세요."}` 반환

### Requirement: 조회 결과 캐싱
The system SHALL cache lookup results per user and query text in Supabase when Supabase credentials are configured, and skip caching silently otherwise.

#### Scenario: 캐시 히트
- GIVEN 동일한 `user_id`와 `text`로 이전에 조회한 기록이 `contextor_history` 테이블에 존재
- WHEN `POST /api/lookup` 호출
- THEN AI를 다시 호출하지 않고 캐시된 `result`를 그대로 반환

#### Scenario: 캐시 미스 후 저장
- GIVEN 동일한 `user_id`/`text` 조합의 캐시가 없음
- WHEN `POST /api/lookup`이 AI 응답을 성공적으로 받아 JSON 파싱을 마침
- THEN 파싱된 결과를 `contextor_history`에 `{user_id, query, result}`로 저장한 뒤 응답 반환

#### Scenario: Supabase 미설정
- GIVEN `SUPABASE_URL` 또는 `SUPABASE_SERVICE_KEY`/`SUPABASE_KEY`가 설정되지 않음
- WHEN `POST /api/lookup` 호출
- THEN 캐시 조회·저장을 모두 건너뛰고 매 요청마다 AI를 호출해 결과만 반환

#### Scenario: 캐시 조회/저장 중 오류
- GIVEN Supabase 캐시 조회 또는 저장 중 예외 발생
- WHEN `POST /api/lookup` 처리 중 해당 예외를 만남
- THEN 캐시 조회 실패는 조용히 무시하고 AI 호출로 진행, 캐시 저장 실패는 로깅만 하고 응답은 정상 반환

### Requirement: 조회 히스토리
The system SHALL expose the authenticated user's lookup history, and a count-only mode, both scoped to `user_id`.

#### Scenario: 최근 히스토리 조회
- GIVEN 인증된 사용자
- WHEN `GET /api/history` 호출 (기본, `count` 미지정 또는 `false`)
- THEN 현재 사용자의 `contextor_history`에서 `id, query, result, created_at`을 생성일 역순으로 최대 10개 반환, `{"items": [...]}` 형태

#### Scenario: 개수만 조회
- GIVEN 인증된 사용자
- WHEN `GET /api/history?count=true` 호출
- THEN 현재 사용자의 히스토리 총 개수를 `{"count": <숫자>}` 형태로 반환

#### Scenario: Supabase 미설정 시 히스토리
- GIVEN Supabase가 설정되지 않음
- WHEN `GET /api/history` 호출
- THEN `count` 여부에 따라 `{"count": 0}` 또는 `{"items": []}` 반환

#### Scenario: 히스토리 조회 중 오류
- GIVEN Supabase 쿼리 실행 중 예외 발생
- WHEN `GET /api/history` 처리 중 해당 예외를 만남
- THEN `count` 여부에 따라 `{"count": 0}` 또는 `{"items": []}`을 반환 (500 에러를 내지 않음)
